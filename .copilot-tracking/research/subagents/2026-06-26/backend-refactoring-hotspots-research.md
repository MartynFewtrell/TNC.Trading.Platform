## Strongest Findings

1. PlatformStateCoordinator is the main backend hotspot because it combines orchestration, policy decisions, retry scheduling, persistence writes, IG session I/O, proof-data capture, event emission, and notification side effects in one class. The constructor injects 13 collaborators and the public entry points immediately drive mutable state transitions rather than delegating to narrower policies or commands. Evidence: src/TNC.Trading.Platform.Application/Services/PlatformStateCoordinator.cs:10, src/TNC.Trading.Platform.Application/Services/PlatformStateCoordinator.cs:28, src/TNC.Trading.Platform.Application/Services/PlatformStateCoordinator.cs:80, src/TNC.Trading.Platform.Application/Services/PlatformStateCoordinator.cs:142. Testability impact: the class is hard to isolate because even simple behavior checks require coordinating runtime state, configuration, retry storage, event storage, notifications, IG client behavior, credential access, proof-data storage, and time. Current tests do not appear to target this class directly, and existing coverage artifacts show it as uncovered, while application unit tests focus on smaller pure components such as TradingScheduleGate. Evidence: test/TNC.Trading.Platform.Application/TNC.Trading.Platform.Application.UnitTests/TradingScheduleGateTests.cs:7.

2. PlatformStateCoordinator duplicates state-transition mechanics across multiple methods, which raises regression risk and forces broad scenario tests instead of precise transition tests. TransitionToActiveAsync, both TransitionToDegradedAsync overloads, HandleSessionExpiredAsync, AttemptImmediateRecoveryAsync, and TriggerManualRetryAsync all set overlapping fields on PlatformRuntimeState and then separately persist retry cycles, events, and notifications. Evidence: src/TNC.Trading.Platform.Application/Services/PlatformStateCoordinator.cs:192, src/TNC.Trading.Platform.Application/Services/PlatformStateCoordinator.cs:358, src/TNC.Trading.Platform.Application/Services/PlatformStateCoordinator.cs:458, src/TNC.Trading.Platform.Application/Services/PlatformStateCoordinator.cs:523, src/TNC.Trading.Platform.Application/Services/PlatformStateCoordinator.cs:571. Testability impact: because transition rules are embedded in async side-effecting methods, there is no small state-machine seam to unit test retry progression, expiry handling, blocked-live handling, or manual retry availability with table-driven tests. Refactoring toward a pure transition engine plus side-effect executors would reduce fixture cost and make branch coverage more meaningful.

3. IG proof-data capture is hidden inside the success path for authentication, which couples the core auth transition to secondary broker queries. After successful authentication, TransitionToActiveAsync invokes TryCaptureLiveProofDataAsync, which performs extra accounts and positions calls and writes proof data while swallowing failures as non-fatal. Evidence: src/TNC.Trading.Platform.Application/Services/PlatformStateCoordinator.cs:379, src/TNC.Trading.Platform.Application/Services/PlatformStateCoordinator.cs:772. Testability impact: validating successful auth behavior currently requires reasoning about both essential session establishment and optional proof-data enrichment. A separate post-auth enrichment service or queued workflow would let tests assert auth recovery independently from proof-data collection and would make failure-mode tests narrower.

4. SqlPlatformConfigurationStore mixes persistence mapping, bootstrap defaulting, configuration parsing, secret updates, and audit composition in one implementation. UpdateAsync mutates the entity, updates protected credentials, builds audit payloads, and saves changes. EnsureConfigurationAsync seeds the durable configuration directly from IConfiguration, parsing enums, dates, integers, notification provider defaults, and bootstrap metadata inline. Evidence: src/TNC.Trading.Platform.Infrastructure/Infrastructure/Platform/SqlPlatformConfigurationStore.cs:49, src/TNC.Trading.Platform.Infrastructure/Infrastructure/Platform/SqlPlatformConfigurationStore.cs:119, src/TNC.Trading.Platform.Infrastructure/Infrastructure/Platform/SqlPlatformConfigurationStore.cs:169, src/TNC.Trading.Platform.Infrastructure/Infrastructure/Platform/SqlPlatformConfigurationStore.cs:182, src/TNC.Trading.Platform.Infrastructure/Infrastructure/Platform/SqlPlatformConfigurationStore.cs:242. Testability impact: the tests need a real EF Core in-memory context plus a real ProtectedCredentialService and data-protection provider even when they are mainly checking bootstrap defaults or restart-required rules. Evidence: test/TNC.Trading.Platform.Infrastructure/TNC.Trading.Platform.Infrastructure.UnitTests/SqlPlatformConfigurationStoreTests.cs:18, test/TNC.Trading.Platform.Infrastructure/TNC.Trading.Platform.Infrastructure.UnitTests/SqlPlatformConfigurationStoreTests.cs:98, test/TNC.Trading.Platform.Infrastructure/TNC.Trading.Platform.Infrastructure.UnitTests/InfrastructureReflection.cs:11, test/TNC.Trading.Platform.Infrastructure/TNC.Trading.Platform.Infrastructure.UnitTests/InfrastructureReflection.cs:20. Extracting bootstrap parsing and snapshot mapping into pure collaborators would enable smaller unit tests without EF or data protection.

5. NotificationDispatcher couples provider resolution, sanitization, persistence, and operational event generation in a single database-writing component. RecordAsync dispatches through the provider, writes NotificationRecordEntity, writes OperationalEventEntity, and saves the DbContext in one method. Evidence: src/TNC.Trading.Platform.Infrastructure/Infrastructure/Platform/NotificationDispatcher.cs:10, src/TNC.Trading.Platform.Infrastructure/Infrastructure/Platform/NotificationDispatcher.cs:28, src/TNC.Trading.Platform.Infrastructure/Infrastructure/Platform/NotificationDispatcher.cs:93. Testability impact: even tests that only want to verify provider-selection or failure classification must instantiate a DbContext and then assert persisted records and events. Evidence: test/TNC.Trading.Platform.Infrastructure/TNC.Trading.Platform.Infrastructure.UnitTests/NotificationProviderTests.cs:81, test/TNC.Trading.Platform.Infrastructure/TNC.Trading.Platform.Infrastructure.UnitTests/NotificationProviderTests.cs:155, test/TNC.Trading.Platform.Infrastructure/TNC.Trading.Platform.Infrastructure.UnitTests/NotificationProviderTests.cs:262. Splitting transport dispatch from audit recording would allow focused unit tests for provider behavior and separate persistence tests for recording policy.

6. OperationalRecordRetentionProcessor contains provider-specific branching that is driven by EF provider capability rather than an explicit abstraction, so tests exercise a fallback path that production does not use. The processor checks Database.IsSqlServer() and runs either ExecuteDeleteAsync or a manual load-and-remove path. Evidence: src/TNC.Trading.Platform.Infrastructure/Infrastructure/Platform/OperationalRecordRetentionProcessor.cs:14. Current tests use the in-memory provider from InfrastructureReflection, so they only validate the non-SQL-Server branch. Evidence: test/TNC.Trading.Platform.Infrastructure/TNC.Trading.Platform.Infrastructure.UnitTests/InfrastructureReflection.cs:11, test/TNC.Trading.Platform.Infrastructure/TNC.Trading.Platform.Infrastructure.UnitTests/OperationalRecordRetentionProcessorTests.cs:17. Testability impact: provider-conditioned logic reduces confidence because the tested behavior is not the production path. A repository seam or provider-agnostic delete abstraction would make unit tests representative and push any SQL-specific verification into targeted integration tests.

7. Time and polling logic are spread across background orchestration and integration fixtures with direct delays, which increases test duration and makes behavior harder to drive deterministically. PlatformAuthSupervisor loops forever with a fixed one-second delay after creating a scope and calling TickAsync. API authentication integration tests wait for readiness through polling with a five-minute timeout and 500 ms delay intervals. Evidence: src/TNC.Trading.Platform.Application/Services/PlatformAuthSupervisor.cs:7, src/TNC.Trading.Platform.Application/Services/PlatformAuthSupervisor.cs:9, test/TNC.Trading.Platform.Api/TNC.Trading.Platform.Api.IntegrationTests/Authentication/PlatformAuthenticationIntegrationTestRuntime.cs:7, test/TNC.Trading.Platform.Api/TNC.Trading.Platform.Api.IntegrationTests/Authentication/PlatformAuthenticationIntegrationTestRuntime.cs:12, test/TNC.Trading.Platform.Api/TNC.Trading.Platform.Api.IntegrationTests/Authentication/PlatformAuthenticationIntegrationTestRuntime.cs:34. Testability impact: direct delays make it difficult to unit test scheduler behavior without waiting on wall-clock time, and they contribute to slow or flaky integration setup. Introducing an explicit tick scheduler or readiness probe retry policy abstraction would allow deterministic tests.

## Prioritized Recommendations

1. Split PlatformStateCoordinator into a pure auth state transition engine and a thin orchestration layer that performs persistence, notification, and IG side effects after a computed decision.
2. Extract IG post-auth enrichment, retry-cycle persistence, and operational-event emission behind dedicated collaborators so successful-auth tests can focus on one concern at a time.
3. Refactor SqlPlatformConfigurationStore into separate bootstrap parsing, entity-to-snapshot mapping, and audit-writing components; keep the store as a composition root over those pieces.
4. Separate notification transport dispatch from notification and operational-event persistence so provider behavior can be tested without EF Core setup.
5. Replace provider-conditional retention logic with a seam that can be exercised consistently in unit tests, and reserve SQL Server behavior checks for narrow integration tests.
6. Introduce abstractions for periodic ticking and readiness polling so scheduler and startup behavior can be validated without real delays.
