# Trading-day market data: application gap research

**Scope:** Compare the [user requirements](trading-day-data-requirements.md) with the [scheduled-process investigation](scheduled-market-data-processes.md) and the checked-out application on 2026-09-26. This is static source research, including the working-tree changes present at inspection time, not a claim about a production run. Recommendations describe desirable behavior and architecture, **not an implementation plan**. No code was changed.

## Overall finding

The application has useful foundations: SQL-backed category interests and last-good instrument/detail data, versioned observations, a time-zone-aware window, fenced collection leases, IG request throttling and a single API hosted-service loop. It **does not yet have a durable, end-to-end "full update"** with the scheduling, triggering, failure recovery and UI semantics requested. The current category/instrument and detail runs are separately keyed to a scheduled slot; a manual POST refreshes categories alone. A listing failure prevents details for *all* selected categories in that slot, and a window close stops work already started. [Collector](../../../src/TNC.Trading.Platform.Api/Hosting/MarketCategoryInstrumentCollector.cs#L15), [detail source reader](../../../src/TNC.Trading.Platform.Infrastructure/Infrastructure/Persistence/EntityFramework/EfMarketDetailListingSourceReader.cs#L45), [manual refresh handler](../../../src/TNC.Trading.Platform.Application/Features/MarketCategories/RefreshMarketCategoriesManuallyHandler.cs#L33).

**Clarification (2026-09-26):** The intended architecture has **one authoritative trading-state determination** used by downstream processes. "Trading Day open", "application able to trade", and "new market-data update permitted" should be distinct outputs of that shared determination, not three independently calculated calendars or a single boolean that conflates operational readiness with time eligibility. A run legitimately admitted while open retains its separate continuation authorization after closing.

## Recommended architectural shape

- **Align the broker calendar and separate day eligibility/window from recurrence.** A single effective Trading Day policy should use the applied broker's configured calendar (including its weekday, weekend and holiday rules) for eligible days, then apply **one shared named-zone start/end** to all market-data processes. Broker calendar settings may be revised to match the intended day; avoid a competing platform window or per-stage hours. Resolve equal slot starts strictly before closing, next eligible start, zero-count behavior and lead-in coverage. Model a slot by broker-calendar date plus slot identity and persist its covered run; compute using local wall-clock boundaries and convert each to UTC. Existing conversion advances nonexistent times to the next valid instant and chooses the first occurrence of repeated times, but slot admission also needs durable deduplication across the repeated hour. [local-time conversion](../../../src/TNC.Trading.Platform.Application/Features/MarketCategoryInstruments/MarketCategoryInstrumentSchedulePolicy.cs#L167), [schedule gate](../../../src/TNC.Trading.Platform.Application/Services/TradingScheduleGate.cs#L57).
- **Compose trading capability once, then consume it everywhere.** Retain/refine `TradingScheduleGate` as the calendar/time policy; put one application-level decision service around it and the *applied* broker's environment, readiness and safety policies. Evaluate against an injected clock and the same effective, versioned configuration, and expose explicit reason codes. Its outputs should distinguish `TradingWindowOpen` (calendar plus shared hours), `CanTrade` (window plus relevant broker/platform trading readiness), and `CanStartMarketDataUpdate` (window plus market-data access and collection prerequisites, independent of the timed update count). Consumers should use those outputs; do not assume a market-data read, authorization to request IG data, or a queued/full update means an order can be placed. Re-evaluate at admission and safety-sensitive transitions, and present the same evaluated state to the UI; avoid caching a time-sensitive boolean beyond its valid instant. A full run admitted while open has a separate fenced `CanContinueAdmittedRun` decision so window closure cannot undo the confirmed post-close completion rule. Existing `TradingScheduleGate` and `AppliedBrokerEnvironmentContext` are reusable inputs, not evidence that this composed service already exists. [gate](../../../src/TNC.Trading.Platform.Application/Services/TradingScheduleGate.cs#L7), [broker context](../../../src/TNC.Trading.Platform.Application/Configuration/AppliedBrokerEnvironmentContext.cs#L3), [manual category refresh](../../../src/TNC.Trading.Platform.Application/Features/MarketCategories/RefreshMarketCategoriesManuallyHandler.cs#L33).
- **Use durable admission rather than in-memory flags.** A SQL-backed run state with a short transaction and fenced, renewable lease can serialize scheduled, manual, catch-up and category-change requests across API replicas. Record which slots each run covers: starts inside the lead-in or occurring while it is running are covered, not queued. A manual/interest run outside those conditions is extra. Interest/settings edits during a run leave the frozen run intact and update one coalesced "reassess after run" intent. On restart, an expired lease resumes an incomplete run without replaying completed stages or overwriting coverage for an already successful slot. Reuse existing transactional publication, environment checks and IG throttle rather than adding a second scheduler.
- **Make fallback and freshness explicit.** Give each stage/item a success time, attempted time, source version and safe failure reason. If category refresh fails, continue on the last good catalogue; if a listing fails, continue details for EPICs in its last validated list. A stale source must not pretend to be a same-slot fresh list. New EPICs absent from fallback are not falsely reported complete. Count a run successful only when all required category/list/detail items were refreshed successfully in that run; otherwise report partial and show which items need attention. Keep a separate read-side last-good pointer and current-run coverage, not one overloaded "current" flag.
- **Enforce provider safety coherently.** Existing approved daily allowance defaults to null and blocks collection; this operational gate and its UI must be reconciled with the promised automatic first update rather than silently removed. Budget reservations must span all three stages, retries and post-close completion, keyed by applied environment and day of run admission; surface insufficient budget, rate limiting and unsupported applied environment as explicit blocked/partial states. Validate large requested counts against real rate limits and window capacity with a **warning**, not a hidden four-update cap. Use short DB transactions for state transitions and keep IG I/O outside locks; retain optimistic revision checks for user interest and lease fencing for workers. See Microsoft's [hosted-services guidance](https://learn.microsoft.com/aspnet/core/fundamentals/host/hosted-services?view=aspnetcore-10.0) (timers can overlap and shutdown cancels work) and [EF Core concurrency guidance](https://learn.microsoft.com/ef/core/saving/concurrency).
- **Expose stable API semantics.** Keep GETs SQL-only and viewer-authorized; add an operator-only manual full-update request and a viewer-readable full-run summary. Return explicit accepted/running, outside-window, validation, unavailable-environment and budget failure results with safe reason codes and run identifiers; never make a read request implicitly contact IG. Align endpoint metadata, configuration DTOs and authorization with the existing Minimal API registrations. [endpoints](../../../src/TNC.Trading.Platform.Api/Features/Platform/MarketCategoryInstrumentEndpoints.cs#L19).

## User experience recommendations

1. On the market-categories overview, place a compact **Market data update** panel above saved data: applied broker/calendar, the shared Trading Day hours and time zone, open/closed (including non-trading calendar days) and the **shared decision's reason** if a new update is unavailable; distinguish this from "able to trade." Show the currently running stage with progress, last result (successful/partial/failed), last successful update, and the next **scheduled start on an eligible broker-calendar day**. For zero scheduled updates, say "Timed updates off"; for no data, say "No data yet" and give the next start when applicable. Offer **Update all market data** only to operators when the shared state permits new market-data admission; if running, replace it with "Update in progress" and do not queue. Keep existing data visible during every state. The current page only polls instrument status every 30 seconds; reuse that lightweight refresh pattern for a consolidated status read rather than live IG calls. [overview](../../../src/TNC.Trading.Platform.Web/Components/Pages/MarketCategories/MarketCategories.razor#L22), [polling](../../../src/TNC.Trading.Platform.Web/Components/Pages/MarketCategories/MarketCategories.razor#L174).
2. Keep the existing category-interest checkboxes. On selection, confirm that a full update was admitted, is already running with a coalesced follow-up, or will await the next opening; on deselection, indicate that saved data is retained as historical. In category rows show distinct **list** and **details** states with last-success times and failed counts. On instrument tabs/details, show item freshness and last success independently of current run progress; identify missing details and failed-only retry time where relevant. The current detail page already displays provenance and correctly warns that quotes are not live. [interest UI](../../../src/TNC.Trading.Platform.Web/Components/Pages/MarketCategories/MarketCategories.razor#L82), [detail page](../../../src/TNC.Trading.Platform.Web/Components/Pages/MarketCategories/MarketDetails.razor#L57).
3. In Configuration, present **one effective market-data Trading Day** for the applied broker: show the broker calendar's eligible weekdays/weekend and holiday exclusions (with access to edit its settings where appropriate), alongside the **single shared** named zone and same-day start/end, count (zero permitted), and lead-in minutes. Preview local slot starts and the next eligible calendar-day start, with DST clarification and a non-blocking >4 warning explaining provider load. Do not present a second unrelated market-data window; make any retained non-market-data schedule purpose explicit. Explain that an active update can finish after close, while a new request/retry cannot start then; distinguish approved provider allowance from number of updates. Use field-level validation and accessible status text rather than relying on disabled buttons or colors alone; see [Blazor forms validation](https://learn.microsoft.com/aspnet/core/blazor/forms/validation?view=aspnetcore-10.0). [existing schedule inputs](../../../src/TNC.Trading.Platform.Web/Components/Pages/Configuration/Configuration.razor#L80), [frequency input](../../../src/TNC.Trading.Platform.Web/Components/Pages/Configuration/Configuration.razor#L197).

## Evidence boundaries and behavior checks

This research did not run the app or tests; runtime timing and quota sufficiency require validation. Especially important acceptance scenarios are: a three-slot 08:00–17:00 London **broker-calendar trading day** (08:00, 11:00, 14:00, never 17:00) and no new work on an excluded weekend/holiday; all three stages agreeing with the **same trading-state service** on opening/closing and the reason for blocked admission; `CanTrade` versus `CanStartMarketDataUpdate` differing when trading readiness and market-data access differ; broker calendar edits recomputing the next eligible start; zero updates with manual/interest allowed on an eligible Trading Day; one late-start catch-up and lead-in/overlap coverage; config edits and repeated interest edits during a run; close during a run versus close before a failed-item retry; failed category/list fallback with partial details; failure of one EPIC while others succeed; no selected categories; restart/second replica lease takeover; unfollowed historical reads; both DST transitions; and correct empty-data/next-start UI. These are *verification cases*, not a delivery sequence.
