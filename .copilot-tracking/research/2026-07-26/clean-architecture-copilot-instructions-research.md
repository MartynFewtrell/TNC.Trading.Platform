# Task Research: Clean Architecture Guidance for GitHub Copilot

Robert C. Martin's Clean Architecture should steer this repository through
explicit source-dependency rules, policy ownership, adapter boundaries, and
testability. It should not be introduced as a mandatory four-project folder
diagram. The recommended implementation is to augment the existing architecture
instruction and add a lightweight allow-list check for production project
references.

## Task Implementation Requests

* Establish the authoritative Clean Architecture principles and rationale
* Separate required architectural constraints from optional conventions
* Assess current repository alignment using source-level evidence
* Reconcile Clean Architecture with Vertical Slice Architecture and CQRS
* Evaluate instruction ownership and executable enforcement alternatives
* Select one implementation-ready approach for future Copilot guidance

## Scope and Success Criteria

* Scope: Robert C. Martin's primary Clean Architecture material, relevant
  publisher-authorized book material, representative production and test code,
  project references, and existing repository customization guidance
* Exclusions: Editing `.github` instructions, refactoring production code,
  choosing a final architecture-test implementation, and creating a migration
  work package
* Assumptions:
  * The current six production projects remain in place initially.
  * A separate Domain project requires demonstrated value and is not a
    prerequisite for adopting the Dependency Rule.
  * Existing Application framework dependencies are a baseline to control and
    reduce incrementally, not evidence that new coupling is acceptable.
* Success Criteria:
  * Primary-source evidence supports the core rules.
  * Repository findings cite exact paths and line ranges.
  * Instruction and enforcement alternatives are compared explicitly.
  * One approach is selected with normative rules, examples, validation, and
    incremental adoption steps.

## Executive Decision

Update `.github/instructions/architecture.instructions.md` as the single owner
of feature architecture and dependency-boundary rules. Extend its activation to
C# project files if the installed host supports the proposed multi-pattern
`applyTo`. Add a closed production project-reference matrix and explain the
composition-root exceptions.

Pair the instruction with a dependency-light XML check that parses production
`.csproj` files through a structured XML API. The check must fail on a forbidden
direct reference, an unknown production project, or a cycle. The enforcement
mechanism remains a delivery decision: prototype a focused test and an MSBuild
target, then retain the form with the clearest local and CI failure output.

This approach creates an immediate ratchet:

* No new reversed production project edges
* No new unjustified Application coupling to outer frameworks
* Boundary representations translated by adapters
* Business decisions kept in Application policy and use cases
* Existing exceptions reduced when their owning features change

## Research Questions Answered

### What Clean Architecture Requires

Martin's controlling rule is about **source-code dependency**, not runtime call
order or directory appearance. Source dependencies point inward toward more
general and stable policy. Inner code must not name outer-layer software
entities or depend on formats generated by frameworks, databases, transports,
or user-interface libraries.

The familiar circles are schematic. Martin explicitly permits more or fewer
boundaries. The architecture therefore does not require four projects named
Entities, UseCases, InterfaceAdapters, and FrameworksAndDrivers.

The desired properties are:

* Business rules remain independent of UI, database, web framework, and other
  external agencies.
* Use cases can be tested without starting external mechanisms.
* Outer details can change without forcing inner policy changes.
* Runtime calls that move outward use dependency inversion where required, so
  the source dependency still points inward.

Sources:

* Robert C. Martin, [The Clean Architecture](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html), 2012-08-13
* Robert C. Martin, [A Little Architecture](https://blog.cleancoder.com/uncle-bob/2016/01/04/ALittleArchitecture.html), 2016-01-04
* InformIT, [The Clean Architecture Dependency Rule](https://www.informit.com/articles/article.aspx?p=2832399), publisher-authorized Chapter 22 excerpt, 2017-11-18

### How the Named Areas Relate

* Entities hold the most general business rules. They may be behavior-rich
  objects or data plus functions; object-oriented entities are not mandatory.
* Use cases hold application-specific policy and orchestrate entities toward
  application goals.
* Interface adapters translate between forms convenient to policy and forms
  convenient to external systems. Controllers, presenters, persistence
  adapters, and service adapters belong here conceptually.
* Frameworks and drivers contain web frameworks, databases, tools, UI
  frameworks, and integration machinery. They are details at the edge.

This repository does not map one project to each area. Application currently
contains both domain-like policy and use-case orchestration. API and Web contain
interface adapters, frameworks, and composition roots. Infrastructure contains
external adapters and frameworks. AppHost and ServiceDefaults support deployment
and hosting outside the canonical diagram. This approximate mapping is valid if
the Dependency Rule and responsibility boundaries remain explicit.

### What May Cross a Boundary

Boundary data should use simple, isolated structures owned in the form needed
by the inner policy. Valid choices include request/response records, basic
structures, arguments, or maps. EF entities, database rows, `HttpContext`, MVC
results, UI component models, and provider SDK responses must not become
Application boundary types.

Interfaces are necessary when a runtime call must move outward against the
allowed source dependency. The inner consumer owns a narrow port; the outer
adapter implements it. Interfaces are not required for every class or every
same-direction call.

```text
Runtime flow: API -> use case -> SQL adapter
Source graph: API -> Application <- Infrastructure
Inner-owned port: Application/IPlatformConfigurationStore
Outer adapter: Infrastructure/SqlPlatformConfigurationStore
Composition: API registers adapter for port
```

### Where Composition Belongs

Martin describes `Main` as the outermost composition detail. In this solution,
API `Program.cs`, Web `Program.cs`, and AppHost are composition roots. They may
reference inner abstractions and concrete outer adapters to assemble the object
graph. That exception permits registration, configuration, adapter selection,
startup orchestration, and hosting. It does not authorize endpoints or AppHost
code to own business decisions.

Evidence:

* `src/TNC.Trading.Platform.Api/Program.cs:1-16` registers Application and
  Infrastructure dependencies.
* `src/TNC.Trading.Platform.Web/Program.cs:1-25` composes authentication, UI,
  presenters, and API clients.
* `src/TNC.Trading.Platform.AppHost/AppHostProjectRegistration.cs:7-46`
  composes executable projects and distributed resources.
* `src/TNC.Trading.Platform.Infrastructure/Infrastructure/Platform/PlatformInfrastructureServiceCollectionExtensions.cs:39-65`
  binds Application-owned ports to concrete adapters.

### How Testing Participates

Clean Architecture makes policy testable without a UI, database, web server,
container, or external service. Martin also treats tests as architectural
participants and rejects one test class per production class as a universal
rule. Stable behavior-facing tests are preferable to tests that mirror volatile
class structure.

Sources:

* Robert C. Martin, [Test Contra-variance](https://blog.cleancoder.com/uncle-bob/2017/10/03/TestContravariance.html), 2017-10-03
* O'Reilly/Pearson, [Clean Architecture digital edition](https://www.oreilly.com/library/view/clean-architecture-a/9780134494272/), public Chapter 28 preview

The repository has a strong layered test portfolio, but its Application test
project references Infrastructure and often creates EF and Data Protection
objects. These tests protect useful behavior but do not prove that Application
policy is independently testable:

## Required Principles Versus Optional Conventions

### Required by the Dependency Rule

* Inward source-code dependency toward policy
* Separation of business policy from replaceable details
* Dependency inversion when runtime control must cross outward against the
  permitted source-dependency direction
* No outer representation or software entity named by inner policy

### Directly Supported Properties and Component Guidance

* Framework-independent policy as a design goal
* Policy tests that do not require external machinery
* Simple, isolated boundary data shaped for inner policy
* Composition at the outermost detail
* Acyclic component dependencies when boundaries are realized as components

### Compatible but Optional

* Vertical Slice Architecture
* CQRS and operation-specific request/response contracts
* MediatR or another mediator library
* Repositories
* DDD aggregates
* A separate Domain project
* Exactly four assemblies or folders
* Microservices or separate processes
* Event sourcing
* A dependency injection container
* One interface per implementation

Martin's [Screaming Architecture](https://blog.cleancoder.com/uncle-bob/2011/09/30/Screaming-Architecture.html)
supports making use cases visible, but it does not prescribe a universal feature
folder taxonomy. His [Clean Micro-service Architecture](https://blog.cleancoder.com/uncle-bob/2014/10/01/CleanMicroserviceArchitecture.html)
treats DLL, process, and service deployment as details.

### Adoption Interpretation

These gaps do not justify a broad rewrite. The initial instruction should freeze
the correct project graph, prohibit new outer framework categories in
Application, and classify existing Application ASP.NET Core and
Microsoft.Extensions use as named migration candidates. Feature work can then
move policy inward or framework adaptation outward one responsibility at a time.

## Relationship to Existing Architecture Guidance

The three architectural concerns are complementary:

* Vertical Slice Architecture controls how behavior for one operation is grouped.
* CQRS controls operation-specific contracts and command/query intent.
* Clean Architecture controls responsibility ownership and source-dependency
  direction across boundaries.

A use-case slice can contain its request, response, validator, and handler while
calling inward policy and consuming an outward port implemented by
Infrastructure. This preserves feature cohesion without allowing the slice to
leak EF, HTTP, UI, or provider types into Application.

Existing instruction ownership supports consolidation:

* `.github/instructions/architecture.instructions.md:1-87` already owns Vertical
  Slice and CQRS-style feature rules.
* `.github/instructions/refactoring.instructions.md:22-68` already requires
  separation, dependency inversion, narrow abstractions, and resistance to
  speculative interfaces.
* `.github/instructions/folders.instructions.md:14-46` prohibits duplicate roots
  and unjustified project structure.
* `.github/instructions/token-discipline.instructions.md:38-51` prefers updating
  the existing owner instead of creating parallel guidance.
* `.github/AGENTS.md:5-21` treats instructions as the first-choice asset for
  stable repository rules.

## Technical Scenarios and Alternatives

### Instruction Ownership

#### Standalone Clean Architecture Instruction

Benefits:

* Gives Martin-specific terminology a prominent home.
* Can span C# and project files.

Limitations:

* Duplicates current architecture and refactoring rules.
* Conflicts with the repository preference for one existing owner.
* Risks loading broad generic guidance for unrelated work.
* Encourages architecture-by-folder naming.

Decision: rejected initially. Reconsider only if the policy becomes too large or
distinct for the existing architecture owner.

#### Augment Existing Architecture Instruction

Benefits:

* Keeps feature cohesion, operation contracts, dependency direction, and
  composition exceptions together.
* Minimizes contradictory or duplicated rules.
* Uses current project vocabulary rather than generic circles.

Limitations:

* Requires careful editing to prevent the file becoming oversized.
* Current `applyTo` omits `.csproj` files.
* Conditional rules must distinguish composition from request handling.

Decision: selected.

#### Scoped Companion for Project Files

Benefits:

* Gives `.csproj` edits a precise matrix with low context cost.
* Separates project graph rules from source responsibility rules.

Limitations:

* Splits one invariant across assets and creates drift risk.
* Adds maintenance before activation or size problems are demonstrated.

Decision: reserve as fallback if the installed host cannot activate the expanded
multi-pattern `applyTo` reliably.

### Executable Enforcement

| Approach | Strength | Limitation | Decision |
| --- | --- | --- | --- |
| XML project-reference check | Directly enforces the six-project allow-list with no new runtime package | Does not detect namespace, type, package, reflection, or friend-access violations | Selected first step |
| NetArchTest | Familiar fluent compiled-assembly rules | Latest public NuGet release found was 1.3.2 from 2021; indirect for `.csproj` edges | Rejected for new adoption |
| ArchUnitNET | Active and capable type, namespace, member, call, and assembly rules | More dependency and API surface than six direct edges need | Reserve for demonstrated source-level rules |
| No executable check | No setup cost | Build accepts newly added forbidden references | Rejected |

Sources:

* Microsoft Learn, [Common MSBuild Project Items](https://learn.microsoft.com/en-us/visualstudio/msbuild/common-msbuild-project-items?view=vs-2022)
* Microsoft Learn, [MSBuild Task](https://learn.microsoft.com/en-us/visualstudio/msbuild/msbuild-task?view=vs-2022)
* [NetArchTest NuGet package](https://www.nuget.org/packages/NetArchTest.Rules)
* [NetArchTest source](https://github.com/BenMorris/NetArchTest)
* [ArchUnitNET NuGet package](https://www.nuget.org/packages/TngTech.ArchUnitNET)
* [ArchUnitNET source](https://github.com/TNG/ArchUnitNET)

Package activity is time-sensitive and must be rechecked immediately before a
future dependency is added.

## Implementation Blueprint Pending Two Delivery Decisions

The normative instruction content and closed dependency matrix are ready for
implementation. Before editing repository instructions or adding enforcement,
verify a supported multi-pattern `applyTo` form and select the permanent XML

### Proposed Ownership and Scope

Update `.github/instructions/architecture.instructions.md` rather than creating
a new file. Proposed frontmatter intent, subject to activation verification:

```yaml
description: 'Enforces Vertical Slice, CQRS-style contracts, and inward Clean Architecture dependencies.'
applyTo: 'src/**/*.cs, src/**/*.csproj, test/**/*.cs, test/**/*.csproj'
```

Verify multi-pattern activation in the installed VS Code host. If unsupported,
use a supported pattern form or a narrow `.csproj` companion. Do not broaden to
`**/*`.

### MUST Rules

* MUST keep direct production project references within the closed matrix.
* MUST keep Application independent of Infrastructure, API, Web, AppHost, and
  ServiceDefaults projects.
* MUST place use cases, policy, inward boundary models, and outbound ports in
  Application while no Domain project exists.
* MUST implement persistence, broker, notification, identity-provider, HTTP SDK,
  and other external adapters in Infrastructure or the responsible outer host.
* MUST translate HTTP, UI, persistence, provider, and SDK representations at
  adapter boundaries.
* MUST keep composition-root access to concrete adapters limited to dependency
  registration, configuration, adapter selection, startup, and hosting.
* MUST let Application own a narrow port when a use case invokes an outer
  adapter at runtime.
* MUST preserve Vertical Slice cohesion within the responsible layer while
  respecting boundary direction.

### SHOULD Rules

* SHOULD keep new Application code free of ASP.NET Core and
  `Microsoft.Extensions` host types; prefer plain inputs, `TimeProvider`, and
  narrow Application-owned abstractions when they protect policy.
* SHOULD reduce existing Application framework dependencies when touching their
  owning feature without blocking unrelated work on a broad refactor.
* SHOULD keep an interface with the consumer that needs it and create it only
  for a real boundary, substitution need, or dependency inversion.
* SHOULD test Application policy without ASP.NET Core, Aspire, a database,
  container, broker, or UI.
* SHOULD extract a Domain project only when independent stability, reuse,
  release, or compile-time isolation justifies the boundary.

### MUST NOT Rules

* MUST NOT add Application references to outer production projects.
* MUST NOT add EF Core, database providers, Aspire, Radzen, transport SDKs, or
  provider-specific authentication types to Application contracts.
* MUST NOT treat API's composition exception as permission for endpoints to use
  EF Core, invoke concrete Infrastructure services, or own business workflows.
* MUST NOT add ServiceDefaults references to product policy or adapter projects.
* MUST NOT require canonical Domain, Core, Entities, UseCases, Adapters, or
  SharedKernel projects without a demonstrated boundary.
* MUST NOT equate Clean Architecture with MediatR, microservices, event sourcing,
  repositories for every entity, or exactly four projects.
* MUST NOT add marker interfaces, pass-through services, or speculative ports to
  make the graph resemble a diagram.

### Examples

Allowed dependency inversion:

```text
Application: IPlatformConfigurationStore
Infrastructure: SqlPlatformConfigurationStore implements the port
API composition root: registers SqlPlatformConfigurationStore for the port
```

Forbidden reversal:

```text
Application handler -> Infrastructure SqlPlatformConfigurationStore
Application request -> Entity Framework entity
Web project -> API project to reuse transport models
```

Allowed composition:

```text
API Program.cs -> Application registration + Infrastructure registration
AppHost -> API and Web executable project metadata
```

### Validation Requirements

* Run the project-reference allow-list check and fail on a forbidden edge,
  unknown production project, or cycle.
* Build `TNC.Trading.Platform.slnx`.
* Run focused Application and affected adapter/host tests.
* Review changed Application package/framework references and imports.
* Review Application boundary types for framework, persistence, UI, and SDK

* Review composition modules separately from request handlers because concrete

## Incremental Adoption Sequence

1. Add the Dependency Rule, matrix, boundary translation rules, and composition
   exceptions to the existing architecture instruction.
2. Verify `.cs` and `.csproj` instruction activation and update the stable lesson
   that dependency invariants, not canonical folders, define adoption.
3. Add the XML project-reference check against the graph that already passes.
4. Record current Application ASP.NET Core and `Microsoft.Extensions` use as a
   baseline. Prevent new framework categories immediately.
5. Move one misplaced policy or framework adaptation at a time when its feature
   changes, preserving focused behavior and adapter tests.
6. Consider ArchUnitNET only after selecting a source-level rule that project
   edge validation cannot express.
7. Consider a Domain project only after cohesive policy demonstrates a need for
   independent compilation, reuse, release, or protection.

## Pitfalls to Avoid

* Treating the four rings as a mandatory project layout
* Confusing runtime flow with source dependency direction
* Calling a DTO clean while it still mirrors an outer schema
* Treating constructor injection as sufficient dependency inversion
* Putting interfaces in a generic shared project instead of with their consumers
* Moving all logic inward, including protocol translation and framework wiring
* Leaving business decisions in Infrastructure because they accompany storage
* Using broad `InternalsVisibleTo` access as a substitute for narrow contracts
* Requiring every use case to have ceremonial abstractions or repositories
* Attempting framework purity through one destabilizing rewrite
